# Disk ANN：按内存预算选择导航码与缓存

更新：2026-09-11。适用数据集：AGNews、GIST、DBpedia。

**核验结论：方向可行，但无常驻码路径和统一有界缓存尚未实现；性能收益尚未证明。** 本文是修改计划，不是完成报告。

## 1. 要解决什么问题

磁盘上保存图和向量表示，内存只用于加速。我们要在相同总内存预算、相同目标召回率下，选择搜索最快的配置，而不是强求把低维1-bit放入内存。

已有完整DB1（完整维度的1-bit码及因子）和低维码实验保留。新增一个基础能力：**不把全量导航码放进内存，也能从磁盘按需取码搜索。** AiSAQ已有压缩码按需读取及内联布局的实现，说明这条路线有依据，但不代表我们的DB1移植已经成功或一定更快。[官方实现](https://github.com/kioxia-jp/aisaq-diskann)

这里有两个独立选择：**导航码是否全量常驻，以及剩余内存缓存多少页。** 无常驻码也可以有缓存；只有专门的零缓存对照才关闭缓存。

## 2. 不同内存下怎么选

| 内存情况 | 候选方案 | 剩余空间 |
|---|---|---|
| 很小，放不下全量码 | 不常驻，按需从磁盘取完整DB1；低维码若放得下也可比较 | 缓存少量页，或关闭缓存 |
| 能放下量化码和部分图 | 比较完整DB1常驻、低维码常驻、不常驻 | 缓存常用图页和数据页 |
| 还有较多富余 | 仍比较上述方案，不强制选某一种 | 扩大缓存，直到预算或可缓存数据用尽 |

这三种情况不是固定的GiB区间：数据量、维度和并发数不同，内存门槛也不同。

“内存为0”只能指**没有常驻数据和跨查询缓存**。查询、候选队列、visited、码本、读盘缓冲仍需要内存。总预算连这些都放不下时，报告不可行，不能承诺零字节搜索。

选择办法只有一条：**在验证集上，先满足内存限制和目标Recall，再选QPS最高的配置；随后冻结配置，用测试集评估。** 放得下不等于最快，维度最大或最小也不一定最好。

## 3. 不常驻1-bit时，搜索怎么做

保留Ours现有图和搜索规则，先只改变完整DB1的获取方式：

1. 按原有规则初始化入口，读取当前扩展节点的邻接表。
2. 找到待评估邻居的DB1和必要因子：缓存命中就使用，否则按页从磁盘读取。
3. 用原有非对称距离计算与筛选逻辑评估这些邻居。
4. 对通过筛选、需要进一步验证的候选读取full4，并立即计算距离。
5. 更新候选池，继续扩展，最后沿用原有重排路径返回结果。

**不是发现一个邻居就无条件读它的full4。** 先读较小的导航码，仍可避免部分full4读取；代价是增加了取码I/O，实际得失要测。

首版需要做的改动：

- 新增页化DB1文件，流式导出完整码及全部因子，记录版本、布局和哈希；保留原图、full4/residual和旧sidecar。
- 增加“内存取码”和“磁盘取码”两种入口，共用相同距离计算。**当前kernel按全局ID索引全量数组，必须把读回记录整理成局部批次并正确映射ID，不能直接给它一段小缓冲。**
- 同一批需要的页去重，读取完成后按原邻居顺序处理。当前Ours每节点先按处理前的候选池筛一次，插入时再按更新后的池筛一次：分批时必须保留这两个时点，不能边读边改变后续邻居的首筛阈值，也不能每批各取前k。
- 同编码、同参数下验证两种入口的距离、候选及结果一致；差异只应来自读取开销。浮点并列使用统一确定性规则。

先不改图拓扑、入口、候选池、终止条件或增加动态beam。若独立取码I/O过高，再单独测试“邻居码内联到父节点记录”；内联会增大索引，可能跨页，不保证更快。

## 4. 降维放在哪一层

降维只生成**额外的低维路由码**，不替换原始数据、不重建图、不把full4改为低维。沿用已有非对称评分，query不二值化；投影码不是原DB1的位前缀。

先保留已存在且维度合法的64/128/256/512维配置。不同数据集使用自己的投影与编码。完整DB1和低维码使用不同评分器，不能套用相同数值阈值，或给低维分数未经证明的原空间下界含义。

低维码允许减少常驻内存、释放缓存空间，但可能丢失有用候选。**末端重排无法找回已经错过的搜索路径。** 因此低维分支必须独立验证Recall；旧的前32截断和ratio=1只作为消融，不默认启用。

已有GIST结果支持“可能省内存，但不一定提速”，不支持普遍收益。详见 [已有诊断](../../results/disk_environment/06_adaptive_disk_ann/gist/LOCAL_NEIGHBOR_DIAGNOSIS_20260911.md)。

## 5. 内存和缓存怎样统一

采用同一个账本：

```text
总预算 = 运行工作区上限 + 常驻码 + 缓存上限 + 安全余量
缓存上限 = 总预算 - 运行工作区上限 - 常驻码 - 安全余量
```

安全余量首版统一预留总预算的10%，它是工程预留，不是内存安全保证。若差值为负，配置不可行。

运行工作区必须包括线程、候选队列、visited、码本/投影、query/评测输入、在途I/O和分配器开销。常驻码包括factor、scale和实际对齐容量。缓存包括页数据、索引结构及查询内复用缓存，不能存在未计费的第二份缓存。

首版采用共享4KiB页缓存和固定LRU规则，缓存图、DB1、full4/residual页；**不另外调热点图比例**，常用图页由缓存自然保留。固定热点图以后单独测，其容量同样从缓存预算扣除。现有“最多缓存10%图节点”的限制只保留为旧版对照。

缓存不足一页则关闭。无缓存也保留必要读盘缓冲；当前计算完毕后释放或复用。在途页、页副本、记录拼接缓冲和重排批次都要分别限额，不能只限制LRU。预算预检应在主体加载前完成，分别保存启动与搜索峰值；重置搜索期RSS统计不能抹去启动超限，不得先读入全量码再卸载。

visited在小内存下可评估精确稀疏集合，但不能保证任意查询占用固定小内存。必须记账并定义超限失败，不能静默丢候选后仍报告正常结果。

硬预算最终用独立授权cgroup验证峰值、OOM和swap。当前核算加RSS的pilot不等于已受硬限制；没有相应权限就保留pilot标签，不修改其他服务的cgroup。

## 6. 怎么保证公平

- **同预算、同目标Recall比较速度**，不强制每种方法使用相同常驻字节数或缓存页数。
- Ours内部比较复用自己的R64/Lbuild400图和同一布局版本；不同预算不重建图。完整DB1的RAM/磁盘取码对照必须保持搜索决策一致。
- 低维分支改变近似评分，属于另一个算法配置，不能称为纯存储位置消融；使用同一候选宽度网格和验证规则，评分专属参数预先声明。
- 自研受控比较共用缓存规则、I/O配置和预热方法。原生外部系统若不能共用实现，单独报告缓存政策、最小内存及布局，不声称策略完全相同；SymQG待内存和读取语义审核后再作二级对照。
- 原生方法不支持的模式标“不支持”，预算不够标“不可行”，Recall未达标标“未达标”，执行错误单独记录。
- 搜索读取必须服务当前扩展或距离计算，不专门读取只为填缓存。物理页附带记录可缓存，但不算已计算候选。预热与启动I/O另报。
- 历史03C/05C曲线若预算、缓存、划分不同，只作背景；公平主表需按本协议重跑，并包含已有Ours基线。

## 7. 按什么顺序实现和测试

| 步骤 | 做什么 | 通过标准 |
|---|---|---|
| 1 | 审计真实内存和保存旧基线 | 明确最小运行内存；不再只用8MiB/worker估算 |
| 2 | 磁盘DB1读取＋局部批次kernel适配 | 微型数据和真实小查询上RAM/磁盘结果与逻辑路径一致，无隐藏全量加载 |
| 3 | 有界工作区与统一缓存 | 零缓存、少页缓存、并发及跨页测试通过；缓存淘汰不改变搜索结果 |
| 4 | 接入无常驻/低维/完整码选择 | 验证集选参后冻结；完整码或不常驻可正常胜出 |
| 5 | 多数据集、多预算评测 | 输出原始日志、Recall–QPS及预算曲线，保留失败点和负结果 |

第2步只验证取码路径，第3步完成前不能宣称支持严格小内存。当前原生代码入口为 `experiments/05_disk_system_fair/native_rust/src/ours_port.rs` 和 `main.rs`，投影/选择器在 `experiments/06_adaptive_disk_ann/`。

测试安排：

- 先微型合成数据，再AGNews集成检查，再GIST和DBpedia；不是只测GIST。
- 总预算统一为256MiB、512MiB、1GiB、2GiB、4GiB。主实验32 workers；1 worker的32/64/128MiB探索另列，不保证可行，也不与主吞吐混比。
- 初始检查width=49、beam=1；Recall–QPS扫描width为16/32/49/64/96/128/192/256/400。Lbuild=400是构建参数，不是搜索宽度。
- 每配置每冷热状态各测1次。冷态清空应用缓存，暖态使用固定验证查询预热；固定I/O方式，正式性能运行不与其他重I/O任务并行。
- 冻结数据/图/编码/二进制哈希、查询划分与配置。已用于诊断的GIST查询可继续做开发回归，但不冒称新独立测试；独立结论需未参与调参的查询。若新增GT，单独版本化，不覆盖旧结果。

所有模式都在每个预算下尝试，不把无常驻限定在最小预算。验证集选出达标配置后按该配置测test，test未达标就报告失败，不能重新挑最好结果。

## 8. 最后看什么、现在能下什么结论

主要交付三类图：**每预算的Recall–QPS、固定Recall的QPS–预算、I/O与实际峰值内存–预算**，同时标出选择的模式/维度、缓存容量及不可行点。

I/O记录实际请求数、读取字节/4KiB扇区、重复读取及各类命中，不能用唯一页数代替总读取。另报尾延迟、启动/预热时间、索引大小。单次运行不提供虚构的重复实验置信区间。full4是较精细的量化表示，不称FP32精确距离；最终Recall对GT计算。
